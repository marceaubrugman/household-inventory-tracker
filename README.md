# Household Inventory Tracker

A Python, PostgreSQL, FastAPI, and Docker household inventory application with both a console interface and a REST API, built with a layered backend architecture.

**Current release: v0.7.0**

## Overview

The Household Inventory Tracker, or HIT, helps users record, retrieve, search, update, sort, delete, and monitor household items.

The project is being developed incrementally as a practical Python data and backend engineering portfolio project:

* **v0.1.0:** Python console application with JSON persistence
* **v0.2.0:** PostgreSQL became the runtime source of truth
* **v0.3.0:** FastAPI added a tested HTTP interface while preserving the console application
* **v0.4.0:** Dockerized local development added with FastAPI and PostgreSQL running through Docker Compose
* **v0.5.0:** GitHub Actions CI added for Python tests, PostgreSQL integration tests, and Docker image build validation
* **v0.6.0:** Added quantity and individual tracking modes with PostgreSQL migrations, database constraints, API validation, and full-stack test coverage
* **v0.7.0:** Added reproducible Docker startup with PostgreSQL and API health checks, readiness-based startup ordering, and automatic first-run schema initialization

HIT now demonstrates:

* a menu-driven console application
* a documented REST API with validated CRUD endpoints
* a shared PostgreSQL-backed data-access layer
* a reproducible local development environment using Docker Compose
* automated GitHub Actions checks for Python behavior, PostgreSQL integration, and Docker image builds

## Item Structure

Every inventory item contains shared descriptive fields and a tracking mode.

A quantity-tracked item represents a supply whose stock level can increase or decrease:

```python
{
  "id": 1,
  "name": "Rice",
  "category": "Food",
  "location": "Pantry",
  "tracking_mode": "quantity",
  "quantity": 2,
  "minimum_quantity": 3,
  "notes": ""
}
```

An individually tracked item represents a distinct durable asset:

```python
{
  "id": 2,
  "name": "Cordless drill",
  "category": "Tools",
  "location": "Garage",
  "tracking_mode": "individual",
  "quantity": None,
  "minimum_quantity": None,
  "notes": "Includes two batteries"
}
```

Quantity-tracked items require non-negative `quantity` and `minimum_quantity` values. Individually tracked items require both fields to be `NULL` and are excluded from low-stock results.

The item ID is generated by PostgreSQL.

## Architecture

HIT provides two application interfaces over shared service, repository, and database layers. Docker Compose runs the FastAPI API and PostgreSQL database as a local multi-container development environment with explicit service health and startup dependencies.

### Console path

```text
app.py
   ↓
inventory_workflows.py
   ↓
item_repository.py
   ↓
database.py
   ↓
PostgreSQL
```

### API path

```text
Uvicorn
   ↓
FastAPI
   ↓
API routers and dependencies
   ↓
item_service.py
   ↓
item_repository.py
   ↓
database.py
   ↓
PostgreSQL
```

### Docker local development path

```text
docker compose
   ↓
api service
   ↓
FastAPI / Uvicorn
   ↓
item_service.py
   ↓
item_repository.py
   ↓
database.py
   ↓
db service
   ↓
PostgreSQL 18
```

FastAPI does not connect directly to PostgreSQL. API requests pass through Python application, service, repository, and database layers. SQL remains isolated inside `item_repository.py`.

Inside Docker Compose, the FastAPI container connects to PostgreSQL using the Compose service name:

```text
db
```

The Docker development database URL is defined in `.env`:

```env
DATABASE_URL=postgresql://hit_user:hit_password@db:5432/hit
```

The console application currently retains its existing workflow layer, while the API uses `item_service.py` as an application-service boundary.

### Layer responsibilities

* `app.py`

  * runs the console application loop
  * routes menu choices
  * handles expected database failures

* `inventory_workflows.py`

  * collects console input
  * applies validation and normalization
  * coordinates repository operations
  * displays results

* `src/api/main.py`

  * creates the FastAPI application
  * registers exception handlers
  * includes API routers
  * exposes health check endpoints

* `src/api/routers/items.py`

  * defines inventory HTTP endpoints
  * maps application results to HTTP status codes
  * returns validated API responses

* `src/api/dependencies.py`

  * connects FastAPI dependency injection to application operations
  * validates item IDs used by read endpoints

* `src/api/schemas.py`

  * defines Pydantic request and response models
  * validates and normalizes API input
  * controls the public response shape

* `src/api/exception_handlers.py`

  * converts known database failures into safe `503` responses
  * logs PostgreSQL operational failures without exposing internal details to clients

* `item_service.py`

  * provides interface-independent application operations for the API
  * coordinates repository calls
  * merges partial updates
  * prevents unsupported fields from being updated

* `item_repository.py`

  * contains PostgreSQL queries
  * performs create, read, update, and delete operations
  * provides search, sorting, and low-stock retrieval
  * keeps SQL out of interface and service code

* `database.py`

  * reads database configuration from `DATABASE_URL`
  * opens PostgreSQL connections
  * applies a connection timeout
  * provides a database connectivity check for `/db-health`

* PostgreSQL

  * stores inventory records
  * generates item IDs
  * enforces data constraints

## API Endpoints

| Method   | Path               | Purpose                            | Success status |
| -------- | ------------------ | ---------------------------------- | -------------: |
| `GET`    | `/health`          | Check API liveness                 |          `200` |
| `GET`    | `/db-health`       | Check API-to-database connectivity |          `200` |
| `GET`    | `/items`           | List all inventory items           |          `200` |
| `GET`    | `/items/{item_id}` | Retrieve one inventory item        |          `200` |
| `POST`   | `/items`           | Create an inventory item           |          `201` |
| `PATCH`  | `/items/{item_id}` | Partially update an inventory item |          `200` |
| `DELETE` | `/items/{item_id}` | Delete an inventory item           |          `204` |

### API behavior

| Situation                              | Response |
| -------------------------------------- | -------: |
| Successful read or update              |    `200` |
| Successful creation                    |    `201` |
| Successful deletion                    |    `204` |
| Item not found                         |    `404` |
| Invalid path parameter or request body |    `422` |
| Database configuration missing         |    `503` |
| PostgreSQL operationally unavailable   |    `503` |

A successful deletion returns an empty response body.

### Example quantity-tracked creation request

```json
{
  "name": "Rice",
  "category": "Food",
  "tracking_mode": "quantity",
  "quantity": 3,
  "minimum_quantity": 1,
  "location": "Pantry",
  "notes": "Basmati"
}
```

The `tracking_mode` field defaults to `quantity` when omitted, preserving compatibility with earlier API clients.

### Example individually tracked creation request

```json
{
  "name": "Cordless drill",
  "category": "Tools",
  "tracking_mode": "individual",
  "quantity": null,
  "minimum_quantity": null,
  "location": "Garage",
  "notes": "Includes two batteries"
}
```

The backend controls generated fields such as the item ID.

### Example partial update

```json
{
  "quantity": 8,
  "notes": "Updated through the API"
}
```

Only supplied fields are changed. Omitted fields retain their existing values.

### Example tracking-mode transition

```json
{
  "tracking_mode": "individual",
  "quantity": null,
  "minimum_quantity": null
}
```

Tracking-mode transitions are atomic. A request that changes `tracking_mode` must also provide both quantity fields in a state valid for the new mode.

## Security and Reliability

HIT includes several defensive programming, testing, and local-development practices:

* parameterized Psycopg queries
* no direct insertion of user values into SQL strings
* allowlisted SQL sort expressions
* allowlisted service-layer update fields
* Pydantic request and response validation
* positive-integer validation for item IDs
* database-level quantity constraints
* credentials stored outside source code
* `.env` ignored by Git
* `.env.example` committed as a safe local-development template
* connection timeout handling
* controlled `404`, `422`, and `503` API responses
* safe public database-error messages
* server-side logging of PostgreSQL operational failures
* isolated PostgreSQL integration-test database
* guarded JSON migration
* atomic migration transactions
* Dockerized local development with separate API and database services
* named Docker volume for local PostgreSQL persistence
* PostgreSQL readiness health checks through `pg_isready`
* API container health checks through the existing `/health` endpoint
* readiness-based API startup through `depends_on: condition: service_healthy`
* automatic first-run schema initialization from `sql/schema.sql`
* read-only GitHub Actions repository permissions
* automated non-integration tests on every push and pull request
* automated PostgreSQL integration tests against an isolated `hit_test` database
* PostgreSQL readiness checks before CI integration tests begin
* automated Docker image build validation on a clean Ubuntu runner

Application validation improves the user experience, while PostgreSQL constraints provide a final data-integrity boundary.

## Docker Local Development

Docker Compose is the recommended way to run HIT locally from v0.4.0 onward.

It starts:

* the FastAPI application container
* a PostgreSQL 18 database container

On a fresh PostgreSQL volume, the database container automatically applies `sql/schema.sql` through PostgreSQL's `/docker-entrypoint-initdb.d/` mechanism. On later starts, PostgreSQL detects the existing database and skips initialization.

Compose waits for PostgreSQL to report healthy before starting the API. Both services expose Docker health status, while `/health` remains an API liveness check and `/db-health` verifies API-to-database connectivity.

### 1. Create the local environment file

Copy the example environment file:

```bash
cp .env.example .env
```

On Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

The `.env` file contains local development settings such as the PostgreSQL database name, user, password, and `DATABASE_URL`.

The `.env` file is ignored by Git and should not be committed.

### 2. Start the application

Build and start the containers:

```bash
docker compose up --build -d
```

Check that the services are running:

```bash
docker compose ps
```

Expected services:

```text
api   healthy
db    healthy
```

The API may briefly show `health: starting` while its health check completes.

### 3. Test the API

Check the application health endpoint:

```bash
curl http://localhost:8000/health
```

Check the database health endpoint:

```bash
curl http://localhost:8000/db-health
```

Expected database health response:

```json
{
  "status": "ok",
  "database": {
    "database": "hit",
    "user": "hit_user"
  }
}
```

### 4. Connect to PostgreSQL

Open a PostgreSQL shell inside the database container:

```bash
docker compose exec db psql -U hit_user -d hit
```

Run a simple database check:

```sql
SELECT current_user, current_database();
```

Exit `psql`:

```sql
\q
```

### 5. View logs

View API logs:

```bash
docker compose logs api
```

View database logs:

```bash
docker compose logs db
```

### 6. Stop the application

Stop and remove the containers:

```bash
docker compose down
```

This keeps the PostgreSQL data volume.

To remove the containers and delete the PostgreSQL volume:

```bash
docker compose down -v
```

Use `docker compose down -v` only when you intentionally want to reset the local database.

### Docker networking note

Inside Docker Compose, the FastAPI container connects to PostgreSQL using the service name:

```text
db
```

That is why the Docker development database URL uses `db` instead of `localhost`:

```env
DATABASE_URL=postgresql://hit_user:hit_password@db:5432/hit
```

## Testing

HIT includes unit tests, API endpoint tests, service tests, migration tests, and PostgreSQL integration tests.

### Continuous integration

GitHub Actions runs three automated CI jobs on every push and pull request. The workflow is defined in `.github/workflows/python-ci.yml`.

The `non-integration-tests` job:

* runs on Ubuntu
* installs Python 3.14
* installs dependencies from `requirements.txt`
* runs `python -m pytest -m "not integration" -v`

The `postgresql-integration-tests` job:

* starts a temporary PostgreSQL 18 service
* creates the isolated `hit_test` database
* applies `sql/schema.sql`
* configures `TEST_DATABASE_URL`
* runs `python -m pytest -m integration -v`

The `docker-build` job:

* runs on Ubuntu
* builds the API image from the committed `Dockerfile`
* tags the temporary image as `hit-api:ci-check`
* verifies that the image can be assembled on a clean GitHub runner

The Docker image is built for validation only. It is not started, published, or deployed.

The PostgreSQL integration-test fixture verifies that the connected database name ends with `_test` before cleaning test data.

### Tests that do not require PostgreSQL

Run:

```bash
python -m pytest -m "not integration" -v
```

These tests use fakes, dependency overrides, and monkeypatching to isolate the API and service layers from PostgreSQL.

Create a separate PostgreSQL database named:

## JSON-to-PostgreSQL Migration

HIT includes a migration tool for importing inventory data from the v0.1 JSON format.

### Validate without writing data

```bash
python -m scripts.migrate_json_to_postgres sample_inventory.json --dry-run
```

### Run a migration

```bash
python -m scripts.migrate_json_to_postgres inventory.json
```

The migration tool:

* validates every record before connecting to PostgreSQL
* preserves existing item IDs
* rejects duplicate IDs
* rejects invalid quantities and missing fields
* requires an empty target table
* imports all records in one transaction
* updates the PostgreSQL identity sequence

The script requires explicit confirmation before writing data.

Private household inventory files should not be committed to Git.

## Database Schema

The current PostgreSQL model uses a single inventory table with tracking-mode-specific quantity rules:

```sql
CREATE TABLE IF NOT EXISTS hit.items (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    category VARCHAR(100) NOT NULL,
    location VARCHAR(100) NOT NULL,
    tracking_mode VARCHAR(20) NOT NULL DEFAULT 'quantity'
        CONSTRAINT tracking_mode_allowed
        CHECK (tracking_mode IN ('quantity', 'individual')),
    quantity INTEGER
        CONSTRAINT quantity_non_negative CHECK (quantity >= 0),
    minimum_quantity INTEGER
        CONSTRAINT minimum_quantity_non_negative
        CHECK (minimum_quantity >= 0),
    notes TEXT NOT NULL DEFAULT '',
    CONSTRAINT tracking_mode_quantity_fields
    CHECK (
        (
            tracking_mode = 'quantity'
            AND quantity IS NOT NULL
            AND minimum_quantity IS NOT NULL
        )
        OR
        (
            tracking_mode = 'individual'
            AND quantity IS NULL
            AND minimum_quantity IS NULL
        )
    )
);
```
Sequential migrations upgrade the frozen v0.5.0 schema, backfill existing records to quantity tracking, relax the previous `NOT NULL` quantity columns, and add the combined tracking-mode constraint.

A single table remains intentional at this stage, keeping the domain model understandable while establishing reliable migration, PostgreSQL, API, and validation foundations.
